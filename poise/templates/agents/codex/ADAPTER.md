# Codex Adapter

## What this provides

| File | Purpose |
|------|---------|
| `WORKFLOW.md` | Symphony-compatible workflow definition |
| `.codex/config.toml` | Registers SessionStart + UserPromptSubmit + Stop hooks |
| `.codex/hooks/session_start.sh` | Prints the harness brief (rules + active plan) via `scripts/session_brief.py` |
| `.codex/hooks/user_prompt_submit.sh` | Plan directive + active-plan re-surface via `scripts/nudge_plan.py` |
| `.codex/hooks/stop_nudge.sh` | Docs-update nudge at session end |

## What it requires

- Codex CLI access (via OpenAI API or Codex app)
- `AGENTS.md` in the repo root (generated by core harness)
- Python 3 on PATH (nudge scripts are shared with the other adapters)

## Entry file

Codex reads `AGENTS.md` natively. No additional entry file needed.

## Hook mechanism

Codex supports `UserPromptSubmit`, `Stop`, `PreToolUse`, `PostToolUse`,
`SessionStart`, and `PermissionRequest` hooks. Every command hook receives
one JSON object on stdin. See [hooks docs](https://developers.openai.com/codex/hooks).

The adapter registers a `SessionStart` hook (the harness brief) plus
`UserPromptSubmit` and `Stop` nudges; all delegate to the shared
`scripts/session_brief.py` / `scripts/nudge_plan.py` / `scripts/nudge_docs.py`
so logic lives in one place across all three agents.

Boundary / style enforcement happens via `lefthook.yml` (pre-commit and
pre-push) — write-time hooks for Codex are not generated by default, but
can be added the same way using `[[hooks.PostToolUse]]` in `config.toml`.

### Plan gate

`scripts/require_plan.py` (the hard plan gate, on by default) is enforced for
Codex via **lefthook pre-commit** — a commit changing more than two source
files with no plan in `docs/exec-plans/active/` is blocked. Codex also exposes
`PreToolUse`, so an edit-time gate can be added once you've confirmed your
Codex version's PreToolUse block format; the commit-time backstop works today
regardless. Disable with `POISE_GATE=0`.

## WORKFLOW.md

The `WORKFLOW.md` file documents the expected agent workflow in plain language.
It is versioned with the code so teams can evolve it over time.

This file is also the integration point with [Symphony](https://github.com/openai/symphony)
— Symphony reads `WORKFLOW.md` to understand how to orchestrate agents across issues.

## Symphony integration

If you are using Symphony as an orchestration layer:

1. Symphony reads `WORKFLOW.md` to understand the task lifecycle
2. Symphony dispatches Codex per issue in an isolated workspace
3. Codex reads `AGENTS.md` for repo context
4. Codex follows `WORKFLOW.md` steps
5. Human reviews output before merge

The harness provides the environment; Symphony provides the dispatch loop.

## Known limitations

- No post-write hook is wired by default — boundary / style violations are
  caught at commit time (lefthook) rather than write time. To add write-time
  feedback, register a `[[hooks.PostToolUse]]` in `.codex/config.toml` that
  calls `scripts/check_architecture.py` and `scripts/check_style.py`.
- `WORKFLOW.md` is a convention, not a mechanical enforcement — the agent
  must choose to follow it.
- The nudges are advisory only — they print to stdout and never block.
